# 共享上下文与系统映射设计

Docs 是人和 AI 共用的持久项目上下文。换一个会话或换一个读者，仍能从项目入口恢复对实际系统的理解，找到设计依据和持续适用的约定，并据此继续工作。[原规则调整预案](https://github.com/Songyanglin-curious/agent-docs/blob/6465c475657d4d50785ae0954ae4a364a0cb9b19/docs/规则调整预案.md)

## 四个核心领域与资料归属

0.1.5 将默认目录收敛为 Project、Design、Rules 和 Knowledge。项目有跨会话行动、暂存资料或环境问题时，先复用已有入口，需要时再加文件。存量项目原有的待办、收集箱或验证材料目录，只要仍有用，就沿用原组织。这样可以从小规模的 Docs 开始，按实际查阅需要扩展。[原规则调整预案](https://github.com/Songyanglin-curious/agent-docs/blob/6465c475657d4d50785ae0954ae4a364a0cb9b19/docs/规则调整预案.md) [组织原则](../references/principles.md)

| 领域 | 读者要解决的问题 |
| --- | --- |
| Project | 系统现在能做什么，实际怎样运行，各部分如何配合，从哪里查实现？ |
| Design | 为什么考虑或采用这个方案，依据、约束和未决问题是什么？ |
| Rules | 在这个项目中持续适用的约定是什么，适用于哪些场景？ |
| Knowledge | 哪些原理、方法或经验值得以后复用，适用条件是什么？ |

归属取决于内容在项目中起什么作用。以外部接口为例，原始契约可作为 Design 的依据，系统如何调用、处理回执及发生失败时如何表现由 Project 描述。相关主题互相链接，原始验证材料供追溯，正文说明结论和验证边界。[组织原则](../references/principles.md)

## 以能力及实际行为建立 Project

0.1.7 将 Project 的完成目标明确为当前系统映射。第一轮结合界面、接口、后台机制、数据、代码和既有资料调查全貌，识别主要能力和系统边界。第二轮沿关键业务活动追踪触发、输入、结果、状态与失败分支，查清组件职责、跨模块交接和共享对象。再把调查结果综合为能解释实际行为的整体，并给出实现入口。[规则调整记录](https://github.com/Songyanglin-curious/agent-docs/blob/6465c475657d4d50785ae0954ae4a364a0cb9b19/docs/开发与验证.md) [初始化建模方法](../references/init.md)

覆盖与表达分别检查。先核对主要能力是否遗漏，再用实际场景检查文档能否解释结果，例如「收到成功回执后，配置是否已经持久化」。同时核对整体介绍与局部说明是否一致，区分代码表明的行为、现场已验证的结果及仍待确认的边界。[Project 质量要求](../references/spec.md#46-project-的质量要求)

## 让读者从问题找到下一步

项目从 `AGENTS.md` 进入 `docs/index.md`，各级索引概括直接子级有什么、何时查看、入口在哪里。根和模块索引承担整体概括，具体机制和分支留在对应主题。Project 随实际行为及认知变化修订，更新局部后检查沿途的上级摘要，失准时再调整。[索引规范](../references/spec.md) [接入与维护注意事项](接入与维护注意事项.md)
