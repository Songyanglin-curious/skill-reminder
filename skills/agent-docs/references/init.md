# Docs 初始化操作指南（init.md）

> **用途：** 指导当前 Agent 在新项目中建立 Docs，或将已有项目接入 Docs。
> **依据：** 初始化前阅读 [组织原则](principles.md) 和 [结构与编写规范](spec.md)。内容归属统一依据组织原则中的模块职责、内容作用与典型内容判断；目录、索引及文档质量遵循结构与编写规范。本文只规定初始化操作、必要模板、权限边界和验收要求。
> **触发：** 仅在用户明确要求初始化、接入或改造 Docs 时执行；日常结束 Hook 不运行本指南。

## 一、执行目标与边界

初始化完成后，应达到以下结果：

1. 人和 AI 能从项目 `AGENTS.md` 找到 `docs/index.md`，再按索引找到需要的知识。
2. 项目已有的有效知识能够被找到和利用；已有实现的项目按 §4.4 建立与实际复杂度相匹配的 Project 当前系统映射，并按 [Project 质量要求](spec.md#46-project-的质量要求) 核对，不能以入门说明代替系统建模。
3. 目录、索引、初始规则和临时证据处理方式符合 `principles.md`，且不破坏既有资料。

**不以“所有旧文件都搬进标准目录”“每个模块都有内容”“生成大量文档”为完成条件。** 初始化不是全面重写文档，更不是日常维护或知识归档。

用户只是询问初始化方案、分类意见或改造建议时，**只分析并回答，不执行文件修改**。

## 二、先检查，再决定做什么

在修改任何文件前，完成以下检查；只读取与判断初始化有关的材料，不要求通读整个仓库。

| 检查项   | 实际动作                                                                    | 需要得到的结果                                                 |
| -------- | --------------------------------------------------------------------------- | -------------------------------------------------------------- |
| 项目边界 | 确定项目根目录、主要子工程、代码与配置位置。                                | 知道 Docs 应服务哪个项目；不误操作上层或其他仓库。             |
| 版本管理 | 检查 Git 根目录、工作区已有改动及 `.gitignore`；非 Git 项目确认实际情况。 | 知道哪些文件已有修改，避免覆盖或误提交。                       |
| 既有导航 | 查找并阅读根 `AGENTS.md`、已有 `docs/index.md` 和相关子项目入口。       | 确认已有导航与项目指令，避免重复或冲突。                       |
| 现有资料 | 盘点指定来源，阅读必要内容及已有引用，按组织原则确定资料在项目中的作用与归属，再按结构规范组织位置与导航。 | 区分有效资料、重复副本和过时记录；不将来源目录名称直接当作其中所有资料的分类结论。 |
| 真实项目 | 综合界面、接口、后台机制、对象数据、代码、配置及可信资料，按 §4.4 调查当前系统。 | 为主要能力、实际行为及重要关系找到依据，识别尚未覆盖或未确认的部分。 |

根据检查结果选择路径：

- **A．尚无 Docs、也无实际实现：** 建立基础导航与空模块索引，不虚构项目结构。
- **B．已有实现、尚无可用 Docs：** 建立基础导航，并按照 §4.4 建立与实际复杂度相匹配的 Project 当前系统映射，不能以最小概览代替初始建模。
- **C．已有 Docs：** 先判断现有索引能否正常使用；以**接入、增补和修复缺口**为主，保留有效结构与内容。

如果 Docs 已能满足上述目标，**不重复初始化**；仅处理明确的缺口并结束。

## 三、确定本次操作范围

执行前形成一份简短的变更清单，至少明确：

- **新建：** 需要新增哪些目录、索引或初始文档；
- **增补：** 哪些已有索引、`AGENTS.md` 或规则需要补充；
- **复用：** 哪些现有资料保留原位，通过链接纳入导航；
- **待确认：** 哪些调整可能影响已有内容或既有约定。

按以下权限处理，**不要把“用户要求初始化”理解为可以任意整理仓库**：

| 操作                                               | 处理方式                                               |
| -------------------------------------------------- | ------------------------------------------------------ |
| 创建缺失的基础目录、索引和导航                     | 在本次初始化授权范围内直接执行。                       |
| 增补 `AGENTS.md` 的 Docs 入口、补充不冲突的索引  | 先读取原文，最小增量修改，避免重复。                   |
| 根据已核实的实际实现建立或完善 Project              | 按 §4.4 调查和建模；只写可确认事实，未核实处不猜测。 |
| 发现现有资料位置不符合新分类                       | **优先建立引用**，不以分类为由直接移动。         |
| 移动、重命名、合并、覆盖或删除既有资料；重组原目录 | 先说明目标、涉及文件和影响，取得用户明确确认后再执行。 |
| 改写已有长期规则、解决相互冲突的规定               | 向用户提出具体取舍并确认；不得静默覆盖。               |
| Git 提交、打标签、重置、暂存全部文件或批量清理     | 不属于默认初始化步骤；只有用户明确授权才执行。         |

需要确认时优先使用当前 Agent 的原生提问功能；不可用则直接提问。用户未答复时不执行该项操作；其他独立且安全的部分可以继续。

用户要求接入或合并资料时，结合请求确定是保留资料集合、重新分类还是补充导航。已授权范围内的常规归类由 Agent 根据内容、项目上下文与已有约定自行完成；关键用途不明、重要结构取舍或内容冲突时再集中提问。复杂迁移可提供简短分组说明，不强制生成逐文件对照表，也不逐份请求分类。

## 四、创建基础结构

### 4.1 标准骨架

**首次创建 Docs** 时，使用统一的初始骨架；没有实际内容的模块只放 `index.md`，不制造正文。**已有 Docs** 不因骨架不同就强制全量重建。

```text
<项目根目录>/
├── AGENTS.md
└── docs/
    ├── index.md
    ├── project/index.md
    ├── design/index.md
    ├── rules/index.md
    └── knowledge/index.md
```

- 模块目录采用上述固定英文名称；普通内容文档**优先使用中文名称**，专业术语及约定的特殊名称除外。
- 每个知识内容目录以 `index.md` 作为入口；有实际子主题时再建立子目录，不预先创建空分类树。
- 不要求四个核心目录都填充正文；不预建待办、收集箱、环境问题文件或对应目录。已有项目保留有效原有结构，包括旧 pending/、inbox/、docs/evidence/，不因新骨架自动迁移。

### 4.2 写好索引，而不是只建立空目录

创建或补充 `docs/index.md`：说明它是当前项目的 Docs 总入口，列出**实际存在**的模块和重要现有资料入口。不要把插件级原则全文复制进来。

创建或补充各知识目录 `index.md`：

- 说明当前目录用途；有内容则提供实际链接。
- 每个导航条目表达**内容摘要**与**使用场景**，不能只写文件名；两者不要重复。
- 空模块可以写“暂无内容”，不添加虚假链接；已有资料暂时留在其他位置时，可以从相关索引链接过去并标明其用途。
- 对已有文档的相对链接，按文件真实位置计算；不能为了让链接好看而复制或迁移资料。
- 每级只索引直接子文件和子目录，子目录链接到其 index.md。先依据子索引概括范围和用途，再向上概括，不拼接下级全文或递归列出后代；按 [索引维护步骤](spec.md#38-索引维护步骤) 检查从根索引逐层可达。

示例（仅用于说明导航条目，不要求固定格式）：

```markdown
- [模块关系与代码入口](project/模块关系与代码入口.md)：介绍核心模块职责和调用关系；定位实现或评估改动范围时阅读。
```

### 4.3 接入 `AGENTS.md`

先检查项目根目录的 `AGENTS.md`：

- **不存在：** 创建最小导航入口。
- **已存在：** 只增补或修正 Docs 入口，保留现有有效指令；已有等效入口时不要重复添加。
- **存在子工程 AGENTS.md：** 保留其原有职责，按实际适用范围处理，不以根目录规则无条件覆盖。

最小导航片段：

```markdown
## 项目知识

本项目使用 [Docs](docs/index.md) 作为人和 AI 共用的持久上下文／共享记忆。
执行相关任务时，从索引按需查阅项目知识及适用规则；结合代码、配置和实际结果核实事实，不必一次阅读全部文档。
```

**不要**把全部模块介绍、索引条目、插件级 `principles.md` / `init.md` / `maintain.md` 复制进 `AGENTS.md`。

Docs 外稳定的项目级资料目录和重要独立入口在 AGENTS.md 登记用途与路径。只服务某个 Design 或其他主题的参考原件，在该主题中链接，通过 Docs 导航查到；临时材料按 4.6 的存放约定查找，不逐文件登记。


### 4.4 为已有实现建立 Project 当前系统映射

按以下方法调查、提炼和表达，产物统一遵循 [Project 内容规格](spec.md#四project-的内容规格)。不能以项目概览、目录骨架或路径清单作为完成条件。

调查过程中保留简短、可核对的工作底稿，连接主要能力、调查依据、覆盖情况与表达位置。底稿不是 Project 正文，不强制新增长期文档：简单项目可留在当前任务上下文，复杂项目可使用临时工作记录；只有需要跨会话续做的事项才进入现有任务入口或待办。

#### 1. 第一轮：建立系统全貌

综合可取得的用户界面与操作、对外接口和协议、主要对象与数据、后台服务及持续运行机制、代码组件、配置、测试、运行结果和已有可信资料，识别系统定位、主要能力、整体组成、外部依赖、主要输入输出及边界。资料是调查线索，涉及现状的结论仍需与实际实现核对；不要求为收集来源额外启动系统或扩大验证。

形成**主要能力清单、发现依据和待查入口**。能力应有可辨认的用途和结果；合并不同入口指向的同一能力，不把每个按钮、接口或类都单列为能力。后台任务、基础服务及框架能力同样属于调查范围。

本阶段建立粗略全貌，不深入全部细节；不将源码目录树当作系统组织，也不将设计规划视为实际能力。清单是待核实、可修正的调查结果，不是天然完整的标准答案。

#### 2. 第二轮：调查主要能力及其实际行为

对清单中的主要能力，选择能够揭示其行为的代表性活动，沿真实入口追踪到结果；必要时继续读取跨模块实现，不能停在“调用某服务”。对会改变结果或理解的重要失败、取消、状态切换等分支一并调查。

每项主要能力需要查清：

1. **用途与参与者：** 完成什么工作，哪些用户、组件或外部系统参与。
2. **触发与输入：** 在什么条件下开始，需要什么对象、数据和配置。
3. **主要行为：** 经历哪些处理和判断，各参与者承担什么职责。
4. **结果与状态：** 何时算成功，改变什么、由谁保存，失败或取消后留下什么。
5. **关系与约束：** 与其他能力、共享对象或外部系统如何交接，有哪些关键限制和必要机制。
6. **实现依据：** 对应哪些实际代码、配置、测试或运行结果，以及进一步查阅入口。

底稿记录**各主要能力的实际行为、关键分支、证据位置及未知部分**。已有准确知识优先复用，对照实现修正失实内容，不为统一结构重复写作。

调查深度按 spec 的必要机制标准判断，不因机制属于内部技术而跳过，也不逐行解读全部实现。代表性活动用于理解一项能力，不能代替对主要能力的覆盖。发现新能力或原有认识错误时回到第一轮修正；两轮是调查阶段，不是两次阅读后必须完成，具体排查仍遵循项目的小步与重试边界。

#### 3. 综合建模与表达

先修正系统全貌，再归纳多条行为共享的对象、状态、职责、交接和约束，形成模型；不能把调查笔记或调用流水直接拼成正文。

1. 从主要能力及其实际行为提炼可理解的说明，把跨模块协作和关键约束讲清楚。
2. 核对共享对象由谁维护、状态何时变化、数据在能力之间如何交接；基础机制设主要说明位置，由相关能力引用。
3. 将主要能力、行为和组成映射到真实代码入口，保留必要证据与未确认边界，不把推断写成事实。
4. 根据实际知识关系组织文档，通过 `project/index.md` 表达整体认知并逐层深入；不预设固定能力树、目录数量或一项能力一篇文档。
5. 将新认识融入已有准确内容，核对整体介绍与局部说明一致，避免孤立模块介绍、重复事实或开发历史。

底稿保留**共享对象、状态、职责、交接、约束及对应表达位置**，供下一步检查。

#### 4. 核对覆盖与表达质量

统一按 [Project 质量要求](spec.md#46-project-的质量要求) 核对覆盖完整性、表达充分性、整体一致性、事实准确性和实现导航，不另设较弱的完成标准。

- 将经多来源核实并修正后的主要能力清单与 Project 对照，记录**已覆盖、未覆盖范围及原因**；能力只出现名称或路径，不算已充分表达。
- 根据实际实现先确定关键事实及证据位置，再选取重要场景或分支，尝试仅依靠 Project 回答并指出文档依据，与事实对照。不能把建模过程中自己知道、但文档没有表达的内容计作通过。
- 核对能力间交接、共享机制以及整体与局部说明；不能以少数能力写得深入代替覆盖，也不要求次要功能等量展开。

独立上下文阅读测试属于规则研发或专项验收方法，见插件的安装与测试说明；日常初始化由当前 Agent 执行上述检查，不强制另起 Agent 或新增验收文档。通过路径、链接检查不能代替语义核对。

#### 5. 处理未覆盖内容

不得编造未经核实的实现。对尚未调查或表达充分的重要能力及行为，明确范围、原因和不确定性；区分已完成映射与仍需补充部分。确需跨会话继续时，复用现有任务入口或按需记录 `docs/待办.md` 并维护索引，不预建待办，不把调查流水写进 Project。

初始化可以分阶段推进，但只完成概览、部分能力或部分模块时不得宣称完整映射；受阻时如实结束并说明缺口，不无限调查。

### 4.5 补充默认 Rules

检查是否已有同类代码注释约定。不存在且无明显冲突时，创建 `docs/rules/代码注释规范.md`；存在则优先沿用，冲突时先询问用户。

默认内容：

```markdown
# 代码注释规范

- 代码注释优先使用简洁、准确的中文。
- 专业术语、API、类名、变量名、协议名称等可保留原文。
- 注释主要说明意图、约束和不直观的行为，避免重复代码字面意思。
- 不强制批量翻译既有英文注释；受外部格式或更具体规范约束时遵循相应要求。
```

创建后在 `docs/rules/index.md` 中注明“编写或修改代码注释时阅读”。**初始化不应顺带修改源码中的注释。**

### 4.6 约定 Docs 外验证材料位置

1. 检查项目已有测试输出、CI 附件和实验产物约定，存在则复用。
2. 没有约定时，使用**项目根目录的 `evidence/`**，不在 docs 下。初始化只记录约定，实际保存材料时再创建目录。
3. 在 AGENTS.md 登记用途与位置；详细规则已有文件时链接原文，不重复复制。可写：“验证材料保存于项目根目录 evidence/（有材料时创建），用于查看测试日志、截图与报告。”
4. 对 Git 项目先核对已有策略和材料用途，只对已明确为临时产物的路径或模式追加忽略规则；不因采用默认目录就忽略整个 evidence/。需要共享或长期追溯的材料允许纳入版本管理。
5. 保留需求不明时，保持文件、忽略规则和跟踪状态不变，必要时集中确认。不得删除旧材料、执行 git rm --cached 或擅自迁移 docs/evidence/；非 Git 项目不创建无效 Git 配置。

正式测试和长期维护夹具仍在工程中，文档必要配图仍随文档组织。新约定不构成扫描或清理既有材料的授权。

## 五、已有项目的接入原则

遇到已有 `docs/`、子工程文档、需求资料或历史记录时，按下面的顺序处理：

1. **先确认作用与归属。** 阅读必要内容及已有引用，依据 `principles.md` 的模块职责、内容作用与典型内容判断，按 `spec.md` 组织位置与导航；资料关联关系有价值时可成组保存，不凭来源目录或文件类型直接判定。
2. **优先保留原位。** 已有内容仍可使用时，通过 `docs/index.md` 或相关模块索引添加导航；即使文件暂时不在标准模块目录，也不妨碍初始化完成。
3. **只补真正缺少的内容。** 缺少导航则补索引；Project 无法正确表达当前系统时，按 §4.4 调查、补充或修正映射，不能以仅补概览作为完成标准；不强迫每份旧资料立刻“归位”。
4. **冲突单独处理。** 对重复、过时、相互矛盾或归属不明的内容，先标识并提出建议；未经确认不合并、删除或迁移。
5. **不改写历史当作当前事实。** 如 `PROJECT_MEMORY.md` 等历史记录，可以作为参考来源或建立导航，不直接视为现行项目规范，也不因迁移而批量改写历史正文。

**初始化的目标是让现有知识可达、当前项目可理解，不是重排仓库。**

## 六、验收与结束

执行完成后逐项核对：

| 验收项   | 通过条件                                                                                |
| -------- | --------------------------------------------------------------------------------------- |
| 入口     | `AGENTS.md` 能引导到当前项目的 `docs/index.md`，原有指令未丢失。                    |
| 导航     | Docs 内容从根索引逐层可达，各级只索引直接子级，摘要能区分查找用途；外部集合从 AGENTS.md 进入，主题参考从主题链接，临时材料按存放约定查找。 |
| Project 映射 | 已有实现的项目按 §4.4 完成调查与建模，并满足 spec §4.6 的统一质量要求；阶段性结果说明覆盖范围和缺口，不冒称完整；无实现项目没有虚构事实。 |
| 存量资料 | 已有有效资料仍可访问，没有未经授权的迁移、覆盖或删除。                                  |
| 初始约定 | 默认代码注释规则已创建或与现有规则核对；Docs 外验证材料位置和保留边界明确，未预建空证据目录或整体忽略 evidence/。 |
| 改动范围 | 只修改本次初始化所需内容；未擅自 Git 提交、打标签或清理仓库。                           |

最后简短报告**新增/修改了什么、复用了什么、哪些事项尚待用户决定**。无法完成的项目说明具体阻碍，不伪称已通过验收。

**满足目标即停止。** 不追加全面文档迁移、全量代码解读、知识提炼或日常 Docs 维护任务。
