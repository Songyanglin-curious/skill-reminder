# Docs 组织原则（principles.md）

> **用途：** 定义 Docs 的组织原则、模块职责及内容归属，供初始化和日常维护共同遵循。
>
> **分工：** 本文说明内容承担什么作用、应归入哪个模块；[spec.md](spec.md) 规定组织与编写要求，[init.md](init.md)、[maintain.md](maintain.md) 分别规定执行步骤和权限。

## 一、目标与原则

**Docs 是人和 AI 共用的持久上下文／共享记忆，用于恢复理解并继续工作。** 保存需要延续的项目事实、设计思考、约定和个人知识，也可保留阶段性认识、遗留问题及环境上下文；不要求记录全部对话或工作过程。使用时结合来源、适用范围与实际实现核实，发现失效内容后在相关范围内修正。

Docs 应支持以下目标：

1. 人和 AI 能从项目 `AGENTS.md` 找到 `docs/index.md`，再按索引找到需要的知识；导航内容符合 [索引规范](spec.md#三indexmd-知识索引与导航规范)。
2. 项目已有的有效知识能够被找到和利用；已有代码的项目应按照 [Project 内容规格](spec.md#四project-的内容规格)，建立基于实际实现的项目认知与代码导航。
3. 内容职责清楚，目录、索引、文档内容及命名符合 [spec.md](spec.md)，且不破坏既有资料。

**不以“所有旧文件都搬进标准目录”“每个模块都有内容”“生成大量文档”为质量标准。** 分类与组织应帮助理解、查找和维护资料。

模块归属与组织规范不构成修改授权；具体执行遵循操作指南及用户要求。

## 二、导航与表达规范

### 2.1 导航层级

使用以下导航关系：

`AGENTS.md → docs/index.md → 各级 index.md → 具体文档`

- **`AGENTS.md`：** 为 Agent 提供 Docs 入口和基本查阅指引。只保留必要的全局导航；不重复列出全部文档或复制具体规则。
- **`docs/index.md`：** 说明当前项目的 Docs 内容与组织情况，是项目知识的总入口，不代替 Project 描述项目实现。
- **目录 `index.md`：** 以导航为目的，概括直接子级的范围、核心内容和查找用途，帮助选择下一步入口。概括所需的背景和关系，不拼接子索引全文，不递归罗列后代文件。
- **具体文档：** 承载知识内容，不依赖阅读整套 Docs 才能理解其主要含义。

**每个实际存在的 Docs 目录都应有 `index.md`。** 空目录可以只有用途说明，不需要虚构导航条目。

新增 Docs 内容必须从 `docs/index.md` 经各级索引可达。维护时先改直接父级，再沿受影响链检查上层摘要；只有范围、用途或重要边界变化才改写，不因下层增加细节而重写所有上层。具体动作见 [索引维护步骤](spec.md#38-索引维护步骤)。

Docs 外稳定的项目级资料入口在 `AGENTS.md` 登记；某个主题的参考原件在对应文档链接，由 Docs 导航到达；临时证据按项目存放约定查找。`AGENTS.md` 不逐文件收录所有外部材料。

### 2.2 命名与表达

- 普通内容文档**优先采用简洁、准确的中文文件名**，直接表达主题；专业术语、产品、协议和代码标识符可以保留英文。
- 约定的目录标识及特殊文件名（如 `project/`、`index.md`、`AGENTS.md`）保持稳定，不为中文化而修改。
- 不强制添加日期、编号或模块前缀；仅在区分版本、时间或同名主题确有必要时使用。
- 文档以清晰、可查阅为优先，按内容选用文字、表格、示意图和代码示例，不统一规定正文模板。
- 原始代码、运行配置、外部资料已有可靠来源时，优先通过链接引用；避免在 Docs 中维护容易过期的冗余副本。必要配图及附件可以随文档就近组织。

## 三、四个核心领域与按需内容

新项目默认建立 Project、Design、Rules、Knowledge 四个目录。其他内容按需使用单文件，复杂后再拆分。目录不是开发阶段，不要求先写 Design、Spec 或任务清单才能实施。

| 模块                | 核心职责                                             | 主要回答的问题                                         |
| ------------------- | ---------------------------------------------------- | ------------------------------------------------------ |
| **Project**   | 描述当前实际软件系统的定位、主要能力、行为、组成、职责及其重要关系。 | 项目现在是什么样？各部分做什么、怎样协作、代码在哪里？ |
| **Design**    | 承载需求与设计输入、参考依据、方案、决策及有价值的演变。 | 要做什么？依据什么？为何这样设计？后来有什么变化？ |
| **Rules**     | 保存持续适用的规范、约定、约束和偏好。               | 在什么场景下、什么范围内，应遵循什么要求？             |
| **Knowledge** | 积累以人的理解和学习为主、也供 AI 查阅的知识与经验。 | 原理是什么？方法怎样使用？有哪些经验与适用条件？ |

内容归属以其在当前项目中承担的实际作用为依据。以下表格明确 Project、Design 与 Knowledge 的主要区别：

| 内容承担的作用 | 默认归属 | 典型内容 |
| --- | --- | --- |
| 规定或解释项目要做什么、需要遵循哪些业务与对接条件，以及为什么这样设计 | **Design** | 需求原件、业务规范、接口契约、编码对照表、协议、需求所附样例、方案与决策 |
| 说明项目当前实际做了什么、如何运行、代码在哪里 | **Project** | 实现说明、实际接口行为、配置使用说明、模块关系、处理流程 |
| 帮助人理解原理、掌握方法或积累经验 | **Knowledge** | 原理解释、技术学习、工程方法、排错经验 |

**典型内容用于帮助理解模块职责，不是穷举清单；具体归属结合内容在项目中承担的实际作用判断。** 不仅凭文件名、格式、来源目录、提供方或维护者决定分类。同一主题可以涉及多个模块，各模块表达自己承担的内容，通过引用建立联系，避免重复保存。

### 3.1 Project：当前系统映射

**Project 是实际软件系统的高层次知识表达，以当前实现为依据，描述系统的定位、主要能力、行为、组成、职责及其重要关系。**

它不承担历史记录职责，不追求复述全部技术实现，而是以足够的抽象层次，让人和 AI 建立对当前项目的正确认识，并能够进一步定位具体实现。

**Project 的内容应该由系统决定，而不是由开发过程决定。**

### 3.2 Design：需求、设计依据与决策认识

**Design 承载项目要做什么、依据什么以及为何这样设计，保存相关输入、方案、决策及演变。**

- 容纳需求、背景、业务与对接条件、原始参考依据、候选方案、决策依据和重要设计演变；按实际主题组织，不强制按模块、时间或状态分类。
- 直接规定或支撑本项目需求、方案设计与系统对接的资料，默认作为 Design 的参考资料。资料的格式、提供方以及相关功能是否已实现，不改变其作为设计依据的职责。
- 允许想法不完整、结论未定、方案并存甚至相互冲突，但应让读者辨认当前结论、分歧和不确定点。
- 保留有价值的取舍及原因，不要求保存每轮讨论；设计被实施或替代，也不必自动删除其历史价值。
- 简单问题可以独立成文；复杂问题按实际需要拆分并相互引用，不强制固定流程和文档模板。

### 3.3 Rules：持续适用的约定

**Rules 是人和 AI 在项目中共同遵循的行为依据。**

- 保存可反复适用的规范、约定、约束及稳定偏好，不保存仅对单次任务有效的指令。
- 一条规则应能辨认适用场景、要求内容、适用范围及约束程度（强制、默认约定或偏好）。
- 以规则或主题自然组织，不强制按项目模块划分；相同规则尽量只有一处主要维护位置。
- 规则与实践或其他规则发生冲突时，应明确其适用条件，避免多份相互矛盾的有效约定并存。
- 用户明确的长期约定可直接维护；同一项目中多次纠正或连续协作明确体现的稳定偏好，也可主动提炼为项目约定。先核对已有规则和相关依据，不凭重复次数臆造约束，不将偏好加重为强制要求。
- 一次性指令不升级为长期规则；尚不稳定的经验按需留在 Knowledge 或原主题。与现行规则冲突、意图不明或需扩大适用范围时先确认，不自动推广到其他项目；不建立候选规则库或审批文件。
- 保留必要来源、背景和适用范围，便于未来跨项目理解与整理；用户修正或取消时更新原规则。

### 3.4 Knowledge：个人知识积累与共享查阅

**Knowledge 是以人的理解和积累为主、同时供 AI 使用的知识空间。**

- 保存知识原理、技术方法、工程技巧、实践经验及值得保留的研究认识；不要求直接对应当前项目或跨项目通用。
- 以知识主题为基本组织单位，可以围绕概念、问题、方法或经验展开；相关内容增多后再自然分层。
- 允许短技巧、长篇笔记和不成熟的认识并存，不强制统一格式；应区分事实、个人理解和推测。
- 注重内容能否被理解、找到和复用，不要求每份知识都形成明确结论或立即指导开发。
- 不承担所有参考资料的收纳职责；资料可供查阅、来自外部或不属于源码，并不足以成为归入 Knowledge 的依据。
- 保留理解和未来跨项目复用所需的来源、条件与上下文，不要求当前实现跨项目聚合或同步系统。

### 3.5 按需单文件

优先复用已有主题或任务入口，没有合适位置时才创建：

- `docs/待办.md`：明确需要跨会话继续处理的行动、下一步或阻碍及原文链接。未决定的想法留在 Design；已完成事项不补待办，完成或取消后更新或移除行动，不另建完成历史库。
- `docs/收集箱.md`：值得保留但暂时无法分类的内容与来源，不自动收录所有对话，不强制定期清空。
- `docs/环境问题.md`：影响后续工作的环境现象、适用条件、已确认处理或当前阻碍；已有部署说明或知识主题时直接更新原文。

名称是可选示例，不预建文件或对应目录。新增后维护直接父级索引；内容确需拆分时再建目录及索引。重要背景保留在相关主题，不因移除行动而删除有效上下文。

### 3.6 Docs 外的验证材料

原始日志、截图、测试输出和审查材料按项目已有约定保存；没有约定时使用**项目根目录 `evidence/`**，在 `AGENTS.md` 说明用途和位置，实际产生材料时再创建，不属于默认 Docs 目录。

测试代码和长期维护夹具仍在工程中；文档必要配图仍可随文档保存。保留期限与 Git 策略按材料用途决定，不直接忽略整个 `evidence/`；不确定保留需求时不删除、不改变跟踪状态。Docs 留下必要结论、条件、验证边界和可靠证据入口，不能只用可能被清理的临时路径支撑重要结论。Maintain 不扫描、整理或清理证据目录。

旧 pending/、inbox/、docs/evidence/ 等已有入口继续有效，不因新默认结构自动迁移、删除或取消跟踪。

## 四、容易混淆的职责边界

| 情形                     | 归属原则                                                                                                                                           |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| 设计方案与实际实现       | **Design** 说明目标、方案和原因；**Project** 说明当前真实实现。两者可关联，但不能互相替代。                                            |
| 已决定的需求与具体待办   | **Design** 保存需求及决策依据；待办按需单文件，只保存仍需跨会话跟踪的行动。 |
| 工程方法与项目约定       | **Knowledge** 解释方法、原理和适用条件；确立持续性要求后，**Rules** 记录应如何遵循。                                                   |
| 验证证据与共享上下文 | 原始材料在 Docs 外按约定保存；影响后续理解的事实、结论和限制进入相关主题，区分已验证与未验证。 |
| 设计参考依据与本项目集成 | 作为本项目需求、方案或对接依据的资料，默认归入 **Design** 的参考资料，可保留原件并建立索引；**Project** 描述实际如何使用和实现这些依据。 |
| 暂时无法判断的资料 | 确实需要保存时可按需用收集箱文件，不为分类扭曲含义。 |

**业务与对接条件作为项目设计输入由 Design 承载；持续适用的开发、协作与维护行为要求由 Rules 承载。** 不因资料中含有“要求”或“规范”字样就归入 Rules。

## 五、原则与操作指南的分工

- **`principles.md`**：定义模块职责、典型内容与分类依据。
- **`spec.md`**：规定目录、索引、引用及文档内容和编写质量。
- **`init.md`**：规定新项目或已有项目怎样建立、接入和检查 Docs，包括必要模板与操作边界。
- **`maintain.md`**：规定日常工作后怎样判断是否需要维护，以及如何创建、更新、整理和确认具体修改。

这四份文件属于插件级通用规则，不要求在每个项目重复保存。分类依据统一维护在 `principles.md`，其余文件引用，不另行建立分类口径。项目自己的 `docs/` 存放实际知识与导航，`docs/rules/` 存放项目适用的规则，而不是插件自身的运行说明。

**总原则：分类为理解服务，索引为查找服务，文档为人和 AI 的持续认知服务；不为了符合目录形式而牺牲实际可用性。**
