# Project 当前系统映射

用当前可核实的实现描述系统边界、组成、主要能力、实际行为、协作及限制。以能力为主线，兼顾用户活动、后台任务、基础服务和框架机制。每项能力是一类具有明确用途和结果的工作，可以有多个入口。

## 调查全貌

综合界面与操作、对外接口、主要对象与数据、持续运行机制、代码、配置、测试、运行结果及可信资料，识别系统定位、组成、输入输出、外部依赖和边界。形成简短可核对的底稿，列出主要能力、发现依据和待查入口。调查中发现新能力或认识错误时修正清单。底稿可留在当前上下文或临时记录，需要跨会话继续时复用任务入口。

## 深入关键业务活动

对主要能力选取代表性活动，从真实入口追踪到结果。沿跨模块链路找出职责交接，核实会改变结果的失败、取消和状态切换分支。为每项能力查清：

- 用途、参与者、触发条件、输入与相关配置。
- 主要行为与判断，各组件职责，以及关键约束和必要机制。
- 成功、失败或取消的含义，状态由谁改变、何时持久化。
- 和其他能力、共享对象、外部系统的交接，实际代码与证据位置，未确认的细节。

凡省略就会误导行为、职责、关系或边界的机制应说明，例如权限判定、时间语义、并发或提交语义。其余实现细节给出定位入口。

## 综合成文

修正整体认识，归纳不同活动共享的数据对象、状态、职责、交接和限制。将经核实的结果写入现有合适主题，从 `docs/project/index.md` 表达系统全貌，按需要深入能力、模块、流程或机制，为关键行为给出实际代码、配置和测试入口。同一共享机制在一处解释，其他主题通过引用关联。文档层级服务于实际知识关系，能力和文件无需一一对应。

已实现行为、联调或运行已确认的结果、未验证边界分别如实表达。Design 可提供形成过程及决策依据；Project 直接修订当前描述，已停用的内容仅在仍影响当前理解时说明。

## 核对质量

| 维度 | 核对 |
| --- | --- |
| 覆盖 | 将经调查校正的主要能力清单与文档对照。注明未覆盖范围和原因。 |
| 充分 | 各主要能力足以解释用途、触发、处理、结果和关键分支。只列能力名称或路径不算完成。 |
| 一致 | 能力之间的交接、共享状态、组件职责与整体说明相符。 |
| 准确 | 结论可追溯到当前实现或观察，未确认的边界可辨。 |
| 可定位 | 从能力行为沿索引能找到真实实现，并知道各入口的职责。 |

从实现先核实若干重要场景及依据，再仅凭 Project 查找答案和文档出处。可检查何时算保存成功、切换状态后还能否操作、失败后留下什么。发现遗漏、冲突或仅靠调查者记忆才能回答时，回到相应主题修正。基础索引、概览或少量能力写得深入都不足以证明完整建模。

维护时只对实际变化涉及的能力及关系做同样的核对。尚无实现时如实呈现现状；覆盖受阻时指出待查范围。
