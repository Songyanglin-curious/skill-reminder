# 日常维护

在当前 Agent 的任务范围内维护现有 Docs。先判断本轮实际确认的变化，再决定需要读哪些资料。检查用户是否要求禁改；当前项目没有 `docs/index.md` 时，轮末检查直接结束。显式初始化使用[初始化](initialize.md)。

| 变化信号 | 检查与维护动作 |
| --- | --- |
| 实现、配置、联调、测试、运行观察或用户提供的可核实事实，可能改变当前系统认知；发现已有描述失实或遗漏 | 检查 Project。即使本轮无代码修改，也需要在相关范围核对新确认的实际能力、行为和限制。 |
| 设计输入或依据有变化，需求、方案或决策已经形成、修订或失效 | 按实际设计问题更新原主题与依据，区分参考原件、未定方案和已确认结论，保留有价值的演变。 |
| 明确建立、调整或取消长期约定，或协作已充分体现稳定偏好 | 读取相关 Rules 和依据，优先修订原主题，说明范围和约束程度。一次性要求不提升为规则，项目偏好不自动推广。 |
| 形成可独立说明、有长期查阅价值的知识或经验 | 在 Knowledge 相应主题保存理解、适用条件与不确定性。 |
| 出现需跨会话跟进的行动、值得保存的未分类资料或环境问题 | 优先更新已有主题或任务入口。无适合位置时使用[按需内容](organization.md#目录与职责)。完成或取消后更新行动。 |

检查后发现文档仍然准确，或讨论未形成可独立保存的认识时，直接结束。拟议意图以现有证据核对，范围外事项由原任务决定。

## Project 影响分析

从实际变化追踪受影响的能力及行为，查看相关输入输出、状态及保存归属、成功与失败条件。顺着能力间交接检查共享对象、组件职责、系统边界、限制和实现位置，确认哪些整体描述、局部说明或索引失准。复用本轮已有的实现核验结果，必要时在当前范围补查。按 [Project 建模标准](project-model.md#核对质量)核对涉及的场景，保留尚未验证的边界。

## 写入与回读

1. 从根和相关索引找到要维护的主题，按[组织与导航](organization.md)确定归属和位置。回读目标文件和直接父级索引，优先把变化融入现有内容。没有适合的原文且内容可独立查阅时创建新主题。
2. 已核实的项目事实、已确认的决定和有充分依据的项目内稳定偏好可以在既定范围内直接更新。关键设计取舍、规则冲突、扩大规则范围、重要资料的迁移或删除以及大规模重组，需要用户决定。对尚待决定的改动先保留，继续已获授权的部分。
3. 补齐直接父级索引，再沿受影响范围检查上层摘要。按事实依据回读改动和链接，确认原文、实现定位与整体说明一致。使用现有证据结论及其边界；不借维护扩大验证、整理证据目录、改动 Skill 规则或提交 Git。

有改动时简述主要结果。无变化时直接结束。受阻时指出具体缺口，不重复发起轮末维护。
