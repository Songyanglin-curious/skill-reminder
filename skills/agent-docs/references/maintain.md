# Docs 日常维护操作指南（maintain.md）

> **用途：** 指导当前 Agent 在正常工作后，检查并维护当前项目的 Docs，使文档跟随实际项目与已确认的认识变化。
>
> **依据：** 执行前按需阅读 [Docs 组织原则](principles.md) 与 [Docs 结构与编写规范](spec.md)。前者定义模块职责和内容边界，后者定义索引、结构与文档质量；本文只规定日常维护的**判断、操作、权限和验收**，不重复介绍模块。
>
> **触发：** 插件在当前 Agent 一轮工作准备结束时提醒；用户明确要求维护 Docs 时也可执行。**不要求关闭整个聊天会话。** 本指南不负责初始化；未建立 Docs 的项目按需使用 [初始化指南](init.md)。

进入 Project 检查时，应读取或使用当前上下文中已读取的 [Project 内容规格](spec.md#四project-的内容规格)，按其 §4.6 的统一标准核对本轮受影响范围；不能仅以路径和链接有效作为完成依据。

## 一、执行目标与边界

一次检查只需回答：**本轮工作产生了什么值得反映到 Docs 的变化？现有内容需要怎样调整？**

维护结果应满足：

1. **项目现状准确：** 实际实现变化或新核实的项目事实若影响 Project 的覆盖与现有认知，应及时修正，不以本轮是否改代码、实现是否正确或任务是否验收通过作为是否同步的前提。
2. **重要认识可追踪：** 仅当本轮形成可独立保存的阶段性结果、明确决定或已发生的状态变化时，才按模块职责维护；讨论尚在进行且没有可保存结果时不写入。
3. **改动范围受控：** 只处理本轮工作直接关联的内容与必要索引，不借机开展全库审计、目录重组或历史整理。

**不以“每轮都有文档改动”“所有模块都检查一遍”“发现不规范就立即整改”为完成条件。**

用户明确要求本轮不维护 Docs 时，不执行本轮自动维护。用户仅询问分类、方案或改造建议时，**不把询问当成同意变更**；除非形成了明确的长期决定，否则只回答，不修改文件。

## 二、先确认本轮变化，再定位文档

Hook 提醒后由**原 Agent 在当前上下文中**完成检查，不启动独立 Agent，也不需要生成单独的检查报告。

### 2.1 识别实际变化

优先利用本轮对话、已执行操作及结果，必要时核对代码、配置、Git 差异或验证材料。只识别与 Docs 有关的变化：

| 变化类型 | 需要确认的事实 |
| --- | --- |
| **实际实现与项目现状** | 功能、行为、职责、结构、接口、数据流或代码位置是否变化？是否经联调、测试、运行观察或其他依据，确认了新的实际能力、行为、限制或此前未知的重要事实？ |
| **设计输入与认识** | 是否新增、更新或明确失效了项目的设计输入与参考依据，或形成、修订、否定了有保存价值的需求、方案或设计判断？ |
| **需延续的上下文** | 是否出现明确需要跨会话跟踪的行动、暂未分类资料或影响后续工作的环境问题；已有记录是否失效？ |
| **长期约定** | 是否确立或改变了长期要求，或同一项目中多次纠正、连续协作已明确体现稳定偏好？ |
| **知识经验** | 是否得到值得人以后查阅、理解或借鉴的知识、方法与经验？ |

**没有明确变化时直接结束。** 变化包括对项目现状的新确认或发现原有描述失实，不限于实际代码改动。本轮对话尚在提出问题、澄清意图或比较可能性，且没有形成可独立保存的阶段性结果时，不为保存对话而制造文档。不把假设写成事实，不把尚未选择的方案写成已定决定。

### 2.2 模块准入判断：先筛选，再读取

**Hook 触发不等于模块需要处理。** 在读取具体文档前，先利用本轮已知信息做一次低成本筛选。未满足准入条件的内容直接跳过，不为了判断而遍历目录，也不输出所有模块的无变化清单。

| 模块 | 进入检查的信号 | 默认跳过的情形 |
| --- | --- | --- |
| **Project** | 本轮可能改变对当前实际系统的认识：代码、配置或重要目录变化影响现状；新增能力或完成集成；联调、测试、运行观察或用户提供的事实确认了能力、行为、职责、关系、边界或限制；发现原有描述失实或遗漏。 | 仅有不影响系统认知和实现定位的内部调整；纯讨论、方案比较或资料查询，尚未确认项目现状；临时文件等不影响 Project 的工作。 |
| **Design** | 新增、更新或明确失效了与项目相关的设计输入与参考依据；或已形成值得保存的需求、设计问题、阶段性方案、决定或重要修正。 | 既无设计输入或参考依据的明确变化，也没有形成可保存的阶段性认识。 |
| **Rules** | 用户明确确立、调整或取消长期约定；或同一项目多次纠正、连续协作明确体现稳定偏好。 | 一次性要求、偏好试探、只有 AI 推测或尚不稳定的经验。 |
| **Knowledge** | 已形成能够独立说明的知识、方法、技巧、经验或阶段性研究认识，且值得以后查阅。 | 只是当下的零散问答、排查中间步骤，或尚未形成可理解认识的讨论。 |
| **按需内容** | 有明确跨会话行动、值得保留而暂未分类的内容，或影响后续工作的环境异常；已有相关记录有确认变化。 | 本轮已完成且无遗留、未决定实施、无可理解内容；不得为填充文件而记录。 |

**准入与更新分开判断：** 符合上表仅表示值得阅读相关 Docs、核对是否需要更新，并不表示必须修改。现有文档已经准确，或变化不影响知识内容时，结束即可。

补充边界：

1. **Project 不是 Git Diff 日志。** 代码、配置和目录变化只是检查线索，不是唯一触发条件。通过实现、集成、联调、测试、运行观察或用户提供的事实，获知重要项目现状、发现原有描述失实或遗漏时，即使本轮没有修改代码，也应主动检查，无须等待用户点名。用户确认的意图不等于实现事实；按已有证据核实，缺少依据时保留不确定性。是否修改以映射是否需要修正为准。
2. **不把“Agent 本轮结束”误认为“话题已经结束”。** 讨论持续中且没有明确阶段性结果时，不制造文档写入，更不应为了决定是否记录而主动打断用户。
3. **不要求所有内容最终定稿。** Design 可保存探索中的阶段性方案，Knowledge 可保存已成形但尚未完全证实的认识，必要的行动和环境上下文可按需记录；关键是边界明确、可独立理解，而不是随口说了一半。
4. **显式请求优先。** 用户明确要求记录、修正或整理指定内容时，可直接按授权范围处理，但仍需遵守模块职责和权限约束。

### 2.3 定位受影响的内容

1. 检查当前项目是否已有 `docs/index.md`；不存在则结束，**不得从日常 Hook 自动初始化**。
2. 根据 2.2 的准入条件，只定位有明确检查信号的主题，不逐个遍历全部目录。
3. 从 `docs/index.md` 和相关目录 `index.md` 查找已有主题与原始资料；按需阅读具体文档，必要时核对实际代码或配置。
4. 判断已有资料是否准确、是否遗漏了变化，以及应当**更新原文、创建新主题、调整待办，还是不处理**。

按 [组织原则](principles.md) 的模块职责、内容作用与典型内容判断归属，再从现有索引定位合适的维护位置。分类依据相同的资料保持一致，不因本轮出现另一种也说得通的组织方式就重新搬迁已有内容。目录、导航和表达按 [结构与编写规范](spec.md) 执行。

能依据资料内容、项目上下文与已有约定确定的常规分类，由 Agent 自行处理；关键用途或重要取舍确实无法确定时再集中询问。分类判断不自动授予迁移权限，日常维护不以重新分类、调整目录为默认动作。

### 2.4 Project 影响分析：从确认事实追踪认知变化

进入 Project 后，先对照相关文档和已核实事实，确定以下影响，再决定改哪些内容：

1. 哪些能力及其实际行为改变，或此前尚未被准确表达？
2. 输入、输出、状态及其保存归属是否变化，成功、失败或取消的含义是否变化？
3. 哪些组件职责、上下游交接、共享对象或机制受影响？
4. 系统边界、外部依赖、约束、限制及实现定位是否变化？
5. 哪些局部说明、整体介绍或索引因此失准，哪些仍准确、可保留？

沿本次变化涉及的关系检查，不逐项审计无关能力；结果留在当前任务上下文即可，不强制新增报告。已有描述准确时结束；缺少关键依据时在相关范围补查或说明未知，不将猜测写成事实。

## 三、按模块决定具体操作

以下是**通过第二节准入筛选后**的日常维护操作规则表。它约束实际应该检查什么、做什么及不能顺带做什么；不要求每轮对全部模块逐项输出判断。

| 模块 | 何时需要处理 | 具体动作 | 不应做的事 |
| --- | --- | --- | --- |
| **Project** | 本轮确认的实现变化或项目事实可能影响当前系统映射。 | 按 §2.4 分析影响，修正受影响能力、行为、组成、职责、关系、边界、限制和定位；必要时补充主题并修正整体介绍及相关索引。 | 不记录开发历史；不把未实现方案写成事实；不为目录整齐迁移资料；不因进入检查就强制改文档。 |
| **Design** | 本轮新增、更新或明确失效了相关设计输入与参考依据，或形成、改变、否定了值得保存的需求、设计认识、方案或决策。 | 更新相关内容、状态、来源与引用；原始资料按 `spec.md` 的参考资料规范组织，与相关方案和实现说明建立必要联系，保留有价值的演变。 | 不因每次小修小改都创建设计；不擅自替用户确定未决方案；不把收到参考资料等同于确认其中全部要求。 |
| **Rules** | 用户明确确立长期约定，或同一项目中已有充分依据的稳定偏好。 | 先读取已有规则和相关纠正依据，优先更新原主题；写清场景、项目范围、要求和必要来源，简述提炼结果。 | 不凭次数臆造约束，不将偏好加重为强制规则；冲突、意图不明或扩大范围先确认，不自动跨项目推广。 |
| **Knowledge** | 已形成值得人长期理解、参考或复用，且可独立说明的方法、原理、技巧或经验。 | 围绕知识主题补充或修正笔记，区分事实、理解与未证实内容。 | 不将普通临时发现、全部对话和每次排错细节自动写成笔记。 |
| **按需单文件** | 明确的跨会话行动、暂未分类资料或环境问题有保留必要。 | 先复用任务入口或已有主题；无合适位置才用 docs/待办.md、收集箱.md、环境问题.md，写必要背景、下一步或处理、原文链接，并接入索引。完成或取消后更新行动，保留有价值背景。 | 不预建文件或目录，不记录所有工作步骤，不重复设计，不强制定期清空或建立完成历史。 |

**一项工作可影响多个模块，但每个模块只维护自己负责的信息。** 已有知识优先更新或引用，不复制多份正文。

原始验证材料由执行验证的步骤按项目约定保存，默认位置及 Git 边界见 [初始化指南](init.md#46-约定-docs-外验证材料位置)。Maintain 只用已产生的结果维护事实、限制和必要依据，不扫描、整理或清理材料目录。已有 pending/、inbox/ 等有效组织继续按需维护，不为改成单文件自动迁移。

## 四、确定权限：直接执行还是询问用户

先判断是否有必要修改，再判断是否具有执行权限。**正确分类不等于获得修改授权。**

| 操作情形 | 处理方式 |
| --- | --- |
| 依据本轮已核实的项目事实，补充或修正相关 Project 能力、行为、职责、关系、限制及实现定位，并调整失准的整体描述和导航 | **直接执行**，限于必要范围；不因此获得迁移、删除或大规模重组权限。 |
| 已有待办、收集内容或环境问题出现明确变化 | **在相关范围直接更新**；完成或取消后更新或移除行动，不另外归档，不删除有价值的背景。 |
| 明确且已获用户确认的设计决定、长期约定，以及已存在主题的事实性补充 | **在既定范围内直接维护**；若涉及新的重要取舍，先确认。 |
| 同一项目多次纠正或连续协作明确体现稳定偏好，且不与现行规则冲突 | **可直接提炼为项目约定**，按第三节核对依据与约束程度，不重复询问；只属不稳定经验时写入 Knowledge 或原主题。 |
| 新规则意图不明、与既有规则冲突、需扩大适用范围；某项设计结论是否已定 | **先询问用户**，不替用户决定；一次性指令不升级。 |
| 迁移、重命名、合并、删除已有重要文档；改变顶层结构或现有规则体系；批量重排资料 | **先提出涉及范围和影响，取得明确授权再执行**。不得借本轮维护自行启动。 |
| Git 提交、打标签、重置、批量暂存或清理仓库 | **默认不执行**；仅当用户另有明确授权时进行。 |
| 修改插件级 `principles.md`、`spec.md`、`init.md`、`maintain.md` 或插件自身配置 | **日常 Hook 不得修改**；只响应用户明确提出的相关修改要求。 |

**提问方式：** 优先使用当前 Agent 可用的原生提问能力；不支持或当前模式无法等待时，通过普通对话询问。尽量集中提出影响后续执行的必要选择，不要求用户审批每个机械改动。

**未取得明确答复时：** 不把沉默视为同意；跳过待确认的变更，其他互不依赖的已授权维护可以继续。不得为等待确认而反复触发 Hook。

## 五、执行维护

对于已确定要处理、且具有权限的变更，按以下顺序执行：

1. **重新读取目标。** 获取待修改文档及直接关联索引的最新内容，避免用旧上下文覆盖新改动。
2. **选择最小修改。** 完整修正本次变化造成的认知偏差，同时不触及无关内容；不以修改字数最少为目标。同一主题优先修订原文；形成独立主题且已有位置不合适时才新增。不得只增加能力名称或路径而遗漏必要行为及关系。
3. **按职责写入。** 归属统一遵循 `principles.md`；Project 按 §2.4 的影响分析，将确认的能力和行为融入当前映射，并修正受影响的组成、职责、关系与限制，不追加开发历史；Design 区分原始依据与设计结论，Rules 依据持续适用的约定，Knowledge 的探索性认识标明不确定性。
4. **维护局部导航。** 按 [索引维护步骤](spec.md#38-索引维护步骤) 先更新直接父级索引，再沿受影响链检查上层概括；摘要失准才改，新增链须从 docs/index.md 逐层可达。不拼接下层全文或展开后代清单。Docs 外重要集合接入 AGENTS.md，主题资料由主题引用，临时证据按统一位置查找。
5. **核对结果。** 检查变更内容与实际依据相符、关联链接有效、未产生不必要的副本或目录、未改动本轮无关资料。Project 按 spec §4.6，在本次影响范围核对覆盖、表达、整体一致性与事实依据；使用已核实的关键场景检查能否从文档得出正确结论，不为验收重新运行开发或全库调查。

补充约束：

- 文档内容与组织遵循 [Docs 结构与编写规范](spec.md)，包括中文文件名优先、索引信息质量、Project 的代码定位能力等；**不能因为发现其他旧文档不合规格就扩展本轮修改范围**。
- 实现即使尚未通过验收或存在缺陷，Project 也应真实反映已经发生且影响项目认知的变化，并注明已知限制；未验证之处不得写成已验证。
- 实施结束时依据用户当前要求、已确认的 Design 或其他有效依据核对本次结果，区分已实现且已验证、已实现未验证、未实现或受阻；不要求先写 Design、另写 Spec 或重复核验清单。Maintain 使用已有核验结果，不接管开发、扩大验证范围或为补齐清单反复续接；候选设计不等于已获实施授权。
- 尊重项目现有 `AGENTS.md`、适用的 Rules 与用户当前要求；发生冲突且无法自行确定优先关系时，不擅自覆盖，应说明冲突并请求决定。

## 六、验收与退出

完成后只检查**本轮受影响的范围**：

| 验收项 | 通过条件 |
| --- | --- |
| 变化对应 | 文档修改确实对应本轮已经发生的变化；没有凭空扩充内容。 |
| 事实与状态 | 当前实现、设计意图、未决问题及验证结果没有混淆。 |
| Project 映射 | 按 spec §4.6 核对本轮影响范围：确认的重要事实得到表达，受影响能力及行为说明充分、关系一致、实现可定位；未用开发记录代替映射，已有准确内容未被强制改写。未完成部分明确说明，不宣称通过。 |
| 范围与权限 | 未迁移、删除或重组未授权的资料；未触及无关文件或擅自提交 Git。 |

- **无需维护：** 直接结束，不创建空报告，也不输出所有模块的“无变化”清单。
- **完成修改：** 简短说明实际修改的文档和主要内容，不输出冗长检查过程。
- **需要决策：** 提出明确问题及影响；未确认的修改不执行，不假称已完成。
- **检查失败：** 保留未完成状态，必要时简短说明；不得阻塞原有工作或无限重试。
- **结束检查：** 同轮防重复与续接由插件 Hook 实现；Agent 不自行再次发起同一轮维护。
