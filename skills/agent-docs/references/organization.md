# Docs 组织与导航

## 目录与职责

首次建立 Docs 时，以 `docs/index.md` 连接四个固定顶层模块。各模块可以暂时只有索引。存量项目优先复用现有有效文档及导航。

| 默认目录 | 职责 |
| --- | --- |
| `docs/project/` | 当前实际系统的映射，覆盖定位、主要能力与行为、组成、职责、关系、代码位置和已知限制。 |
| `docs/design/` | 以设计问题为单位，记录需求、背景、参考依据、候选方案、决策理由和重要演变。未定意见可保留并标明状态。 |
| `docs/rules/` | 可重复适用的项目行为约定、约束与偏好。写清场景、要求、范围、约束程度及必要来源。 |
| `docs/knowledge/` | 以人的理解和积累为主、同时供 AI 查阅的原理、方法、技巧、经验和研究认识。注明来源、适用条件和不确定性。 |

按内容在当前项目中承担的作用确定归属。例如，供应方的接口契约作为对接依据归 Design；当前实现如何调用接口及处理结果归 Project；长期适用的协作或开发要求归 Rules；对技术原理的经验性解释归 Knowledge。同一主题跨模块时，通过引用连接各自的内容。

Design 的参考资料可保留原位，由相关主题链接。资料较多时，可在 `docs/design/参考资料/` 建索引，说明性质、用途及必要的来源、版本、适用性。按实际关联成组，确需保存副本时说明来源。稳定、独立的项目级外部资料集合在 `AGENTS.md` 标明入口和用途，主题参考件从相关主题访问。

待办、暂未分类的有价值内容和影响后续工作的环境问题优先补到已有主题，必要时使用 `docs/待办.md`、`docs/收集箱.md` 或 `docs/环境问题.md` 等单文件。只保存确需跨会话跟踪的行动及原文链接，完成或取消后更新行动并保留有价值的背景。已有 `pending/`、`inbox/` 或 `docs/evidence/` 有效时继续沿用。独立内容增多后再分层。

普通文件用简洁、准确的中文名，可保留技术术语、标识和已有命名。章节和载体按需要选择，文档配图可就近放在同名 `.assets/` 目录。以现有可靠资料为主要来源。

## 索引与根导航

根 `AGENTS.md` 指向项目 `docs/index.md` 并说明按需查阅，保留现有指令。根索引概括 Docs 的范围与各模块用途；模块索引说明本模块如何理解与使用；下级索引帮助读者定位具体主题。索引本身可以承载当前层次所需的知识，尤其是 Project 的整体概览、能力关系和深入入口。

每个知识目录有 `index.md`。各级索引只导航直接子文件和子目录，子目录链接到其 `index.md`；从根索引逐层可达。为每个重要入口写明主要内容、关系和使用场景，读者应能用实际查找问题选到下一跳。源码、相关主题和证据可补充链接。图片等资源目录按所属文档查阅。

维护索引时先读目标文档、直接父级索引，需要概括子目录时读子索引；修改直接父级后沿受影响链向上检查。只有范围、用途、核心能力或重要边界变化导致上层摘要失准时才改上层。检查链接、引用状态和导航是否可用；获授权移动、改名或删除资料时同步相关引用。

## Evidence

测试日志、截图、报告和审查原始材料按项目已有约定保存；没有约定时，在项目根 `evidence/` 按实际产生的材料存放，并在 `AGENTS.md` 说明用途和位置。正式测试和长期夹具留在工程原位。临时材料按统一位置查找，稳定且支撑重要结论的证据通过相关主题链接。正文说明核实的结果、条件、限制和依据。

按材料的保留及共享需求决定 Git 跟踪。仅对已确定为临时的路径或模式配置忽略，已有资料和跟踪方式需变动时先确认。日常维护使用已取得的结果，证据目录的盘点或清理由独立任务授权。
